# 本地团购 SaaS 试点

面向平台管理员、代理商、商家和门店核销员的多租户团购试点。当前交付为本地演示版本：模拟支付、PostgreSQL 交易库、管理后台及两个原生微信小程序模板。

## 代理合作与收费边界

平台代理合作费和 SaaS 服务费均在线下对公账户收取，不进入本系统。本系统不保存收款金额、付款账户或凭证，不发起扣费、代扣、分账或自动续费。

- 仅平台系统管理员可以创建、停用代理商账号，以及确认或调整其线下合作对应的开通授权；代理商不能自行购买、续期或增加名额。
- 按次合作：系统只记录可提交的“商家小程序开通”名额。代理提交一家的开通资料时暂占 1 个名额；平台确认小程序可发布后记为已使用；审核失败自动归还。
- 年度合作：系统只校验年度有效期，在有效期内可为任意数量的新商家提交小程序开通资料。
- 名额用完、年度到期或代理被停用，只会阻止该代理提交**新的商家小程序开通资料**。代理仍可建立草稿；已经开通的商家小程序、套餐销售、已售券履约与门店核销均不受影响。

项目中的订单、退款和对账功能仅用于消费者交易的业务记录与支付服务商回调核对，不是 SaaS 或代理合作费的收款模块。实际接入收钱吧等支付服务商时，应由对应适配器处理支付/退款回调，平台不得归集或挪用商家交易资金。

## 启动

1. 运行 `npm install`，再运行 `npm run doctor` 验证新电脑的源码与依赖是否完整。
2. 运行 `npm run dev:api`。
3. 新终端运行 `npm run dev:admin`，打开 `http://localhost:5173`。

需要在未安装 Docker 的电脑上验证四个角色的独立入口时，运行 `npm run dev:workspaces`。它会先等待 API 完成编译、演示种子初始化并监听 3001，再启动 `http://localhost:5173`、`http://localhost:5174`、`http://localhost:5175` 与 `http://localhost:5176`，避免页面已经打开但登录接口尚未就绪；四端按精确来源端口启用“来源只能登录指定角色”限制。若浏览器、代理软件或本机 hosts 无法解析 `localhost`，可将每个地址中的 `localhost` 替换成 `127.0.0.1`；两种本机回环地址都映射到相同角色。启动前请关闭已运行的 `dev:api`、`dev:admin`，按 `Ctrl+C` 可一并停止四个工作台。

`npm run doctor` 不会读取或打印 `.env` 内容；它只检查 Node.js 版本、工作区源码、依赖、演示部署配置和本地 API/四个角色端口状态。需要验证 Docker Desktop 是否已安装时运行 `npm run doctor -- --docker`。

本地开发或测试环境未设置 `DATABASE_URL` 时，API 自动使用 PostgreSQL 兼容的内存演示库，因此无需本机数据库即可走完整模拟闭环。设置了 `DATABASE_URL` 的本机 Docker 演示必须显式设置 `NODE_ENV=development` 和 `ALLOW_DEMO_MODE=true`，之后才会使用真实 PostgreSQL 并写入演示数据；也可复制 `.env.example` 后运行 `docker compose up -d postgres`。任何连接真实数据库但未显式允许演示模式的开发部署都会按共享环境失败关闭。`staging`、预发及其他共享环境必须配置真实数据库，禁止回退到内存演示库，也不会自动写入演示商家、默认账号或允许公开演示顾客会话。

使用 Docker 演示完整后台、API 和 PostgreSQL 时，运行 `docker compose up --build`。API 镜像自身默认使用 `staging` 共享环境安全模式，必须提供真实数据库和完整运行配置；本地 Compose 会显式覆盖为 `NODE_ENV=development` 与 `ALLOW_DEMO_MODE=true`，不会让镜像的开发模式意外进入其他部署。编排会先执行一次迁移，启动两个无状态 API 副本、一个独立生命周期 Worker 和内部 API 网关，再启动四个独立角色的 Nginx 工作台：`http://platform.localhost:5173`、`http://agency.localhost:5174`、`http://merchant.localhost:5175` 与 `http://verify.localhost:5176`。数据库、Worker、API 和内部网关都不暴露宿主机端口；工作台 Nginx 是唯一入口，内部网关只对连接级失败切换到另一 API 副本，绝不重放 POST。两层受控代理保留同一 `X-Request-Id` 并通过 `TRUST_PROXY_HOPS=2` 传递真实客户端地址。该编排固定为本地/演示模式，不能用于真实消费者交易或绕过生产支付、微信身份与注册适配器闸门；生产子域名与 TLS/WAF 配置见 [SUBDOMAIN_DEPLOYMENT.md](SUBDOMAIN_DEPLOYMENT.md)。

Docker-capable 开发机和 CI 应运行 `npm run smoke:docker`。该命令使用受限的 `localdealssmoke-*` 临时项目和独立数据卷，自动完成镜像构建、真实 PostgreSQL 迁移及重复迁移、双 API/独立 Worker/内部网关健康检查、四工作台角色清单校验、限量库存并发下单、并发支付确认只生成一组券、并发核销单券原子性、全局止售同键重放与双人恢复、通知、审计和支付 outbox 双进程竞争领取、陈旧 `PROCESSING` 任务恢复、供应商消息/支付引用唯一性、订单支付引用一致性、审计载荷篡改隔离、审计链完整性、支付 outbox 行锁超时与提交前连接中断回滚、单 API 副本故障切换和 Worker 隔离恢复；无论成功或失败都会清理本次临时容器、卷和本地构建镜像，并在 `artifacts/docker-smoke-*.json` 留下不含环境变量、令牌、密码、收件人或业务正文的证据报告。最新证据 `artifacts/docker-smoke.json` 记录了配置 250ms、实测 264ms、SQLSTATE `55P03`，并证明被终止的持锁事务回滚到 `PENDING` 且 `attemptCount=0`。它不会操作普通 `localdealsprod` 或手工 Compose 项目，也不替代签约通知与真实支付通道的失败注入。

发布前运行 `npm run release:verify`。它不读取或打印 `.env` 值，但会校验子域名服务、精确角色构建参数、内部 API 代理和工作台安全头；随后依次执行全仓 lint、API 测试、API 构建，以及平台、代理、商户、核销四个角色包的独立构建。每个包都生成无敏感信息的 `workspace-manifest.json`，其中角色、同源 API 路径和发布版本必须和部署入口一致。共享环境必须设置非敏感的 `RELEASE_ID`；它会出现在 API 健康响应、`X-Release-Id` 和工作台清单中，方便灰度排障与安全回滚。

后续开发、排障与无中断更新的统一规则见 [MAINTENANCE_ENGINEERING.md](MAINTENANCE_ENGINEERING.md)；数据库发布的执行顺序见 [ZERO_DOWNTIME_RELEASE.md](ZERO_DOWNTIME_RELEASE.md)。

真实 PostgreSQL 不再由应用启动时自动改表。首次部署或升级时，由单个受控部署任务运行 `npm run migration:run -w @local-deals/api`（该命令会先构建 API）；应用实例保持 `RUN_MIGRATIONS_ON_STARTUP=false`。旧演示库连接迁移前先备份，初始迁移可安全补齐缺失表和索引，但不会替代正式变更评审。试点阶段的“商家主体”只是申报名称，可能同名、改名或尚未核验，绝不能作为数据库唯一键；商家创建改以发起账号的请求幂等键防止双击和网络重试。平台经营状态变更也会将同一操作者、商家和 `Idempotency-Key` 固化为命令记录：相同内容重试返回既有商家状态，不会重复写审计；同键改动状态、原状态、说明或同时提交的资料/合同内容返回 `409`。已发布旧工作台不带该请求头仍兼容，切换新版平台工作台前必须先完成 `merchant_status_change_commands` 的受控迁移。真实主体核验接入后，才应以经合规审查的统一社会信用代码/登记号派生的受控稳定标识绑定工作区，不能自动合并、删除或改写历史交易和审计数据。

共享环境会拒绝 `RUN_MIGRATIONS_ON_STARTUP=true`，避免多实例滚动更新时争抢 schema 锁。每次发布前运行 `npm run migration:verify`，并按 [ZERO_DOWNTIME_RELEASE.md](ZERO_DOWNTIME_RELEASE.md) 的 expand → backfill → contract 流程执行；回滚应用版本时不自动回滚数据库迁移。

完整的试点边界、正式主体模型、真实交易闸门和下一批生产治理改造见 [PRODUCTION_READINESS.md](PRODUCTION_READINESS.md)。

## PostgreSQL 备份与恢复演练

生产数据库必须由独立计划任务执行加密备份，不能依赖 Docker 卷或应用实例磁盘。仓库提供可审计的 PostgreSQL 自定义格式备份工具：`pg_dump` 生成临时文件后，工具用独立的 `BACKUP_ENCRYPTION_KEY`（32 字节 Base64）以 AES-256-GCM 加密，再原子写入密文和带 HMAC 认证的 SHA-256 清单。状态检查会验证清单认证码、加密文件头、密钥标识、密文大小、摘要及创建时间，并拒绝未来时间或伪造文件。脚本不输出连接串、密码、密钥或明文数据。

```powershell
# 计划任务或受控运维任务：需安装 PostgreSQL 客户端并注入密钥管理服务提供的环境变量。
$env:DATABASE_URL = '<受控数据库连接串>'
$env:BACKUP_ENCRYPTION_KEY = '<32字节Base64密钥>'
$env:BACKUP_ENCRYPTION_KEY_ID = 'backup-2026-q3'
$env:PG_BACKUP_OUTPUT_DIR = 'D:\secure-backups\local-deals'
$env:BACKUP_RETENTION_DAYS = '30'
npm run backup:postgres

# 监控任务：默认 RPO 为 24 小时，超过阈值返回非零退出码。
$env:BACKUP_MAX_RPO_HOURS = '24'
npm run backup:status
```

加密产物和清单应由受控任务上传到具有版本保留与不可变策略的 COS 桶；本地 `backups/` 和 `backup-drills/` 已被 Git 与 Docker 构建上下文排除。每月至少一次恢复到独立、隔离且库名以 `_drill`、`_restore` 或 `_test` 结尾的目标库：

```powershell
$env:BACKUP_FILE = 'D:\secure-backups\local-deals\local-deals-postgres-<时间>.dump.enc'
$env:RESTORE_DATABASE_URL = '<隔离演练库连接串，数据库名必须以 _drill/_restore/_test 结尾>'
$env:BACKUP_RESTORE_DRILL = 'true'
$env:BACKUP_MAX_RTO_MINUTES = '120'
npm run backup:restore-drill
```

恢复脚本会验证核心交易、券、售后、审计和支付事件表，并写入不包含数据内容的 RTO/行数证据报告。首次生产部署前必须成功完成一次备份、COS 上传、RPO 检查和恢复演练，之后将状态检查与演练失败接入告警。

真实 PostgreSQL 部署中，生命周期任务默认关闭。单独选择一个工作实例设置 `RUN_LIFECYCLE_WORKER=true`；系统会用 PostgreSQL 顾问锁避免误配的多实例重复推进订单超时、券过期、合同和账单。内嵌演示库仍默认自动执行这些任务。普通 API 实例使用 `/api/v1/public/health/ready`，工作实例必须由监控探测 `/api/v1/public/health/worker`：公网探针仅返回最小 `status` 和通用失败信息，数据库模式、迁移状态、连接池、队列和 Worker 时间等诊断数据只对平台运营、平台安全和系统管理员开放于 `/api/v1/platform/health/ready` 与 `/api/v1/platform/health/worker`。探针仍会验证运营日历、数据库、迁移和 Worker 时效，避免内部细节被公开枚举。`LIFECYCLE_WORKER_MAX_STALENESS_SECONDS` 只能设置为 120 至 900 秒；工作器错误、停摆或误配置不能再被单纯的数据库健康检查掩盖。完整生命周期 sweep 的间隔由 `LIFECYCLE_SWEEP_POLL_INTERVAL_SECONDS` 控制，共享/生产默认 60 秒（允许 5 至 300 秒的受控值）；审计 outbox 与订单/券过期队列分别由同一 Worker 在 `AUDIT_OUTBOX_POLL_INTERVAL_SECONDS`（默认 5 秒）和 `EXPIRY_SWEEP_POLL_INTERVAL_SECONDS`（默认 10 秒）独立批量推进；三类任务共用顾问锁，不允许多个 Worker 交错推进状态。本地 `npm run dev:workspaces` 会自动以单 Worker、5 秒 sweep 运行，确保导入、批量操作和导出演示在短时间内完成；生产 Docker 仍保持 API 与 Worker 分离。

同一探针还会报告逾期订单和未标记过期券的数量及最早积压时间。过期快速循环每 10 秒运行，每次分别最多处理 `EXPIRY_SWEEP_BATCH_SIZE`（默认 200）条订单和券；`EXPIRY_QUEUE_MAX_AGE_SECONDS` 默认 600 秒，最早积压超过该阈值会返回 `503`，即使 Worker 仍在周期执行也会触发告警。已投递支付的超时订单在释放库存前必须查单；同一支付意图 60 秒内已查过则暂时保留订单与库存，冷却结束后再查，避免通道抖动导致高频外呼或把延迟成功的订单错误关闭。

顾客套餐详情、券包和运营检查不会触发全租户过期扫描或支付查单。过期订单和券仅由生命周期 Worker 分批推进；顾客可购额度会立即排除自身已超时的待支付订单，但套餐总库存会保守地等待 Worker 完成付款对账和库存回补，避免支付结果延迟时超卖。

顾客公开读写接口在服务端按顾客身份限流：下单、模拟支付确认、动态码、退款和售后创建均采用更严格的窗口；兼容旧客户端的完整券包和顾客售后列表也限制为每分钟 60 次。超限返回 `429` 和重试秒数，窗口到期自动恢复；限流身份在数据库中只保存 HMAC 键，不保存顾客身份原文。

登录失败封禁和请求限流均使用单条数据库原子 upsert 计数：并发请求会按实际取得的计数决定是否放行或封禁，不会因“先读后写”使配额内请求被误拒绝或让失败计数落后。真实 PostgreSQL 仍是多实例并发语义的最终验收环境；本地内存演示库只用于功能回归。

生命周期 Worker 每轮最多清理 1,000 条过期请求限流或登录失败记录；`IDX_login_throttles_reset_at` 由在线迁移创建，必须在启用新版本前先由受控迁移任务执行。这样随机账号密码喷洒不会令限流表无限增长，也不会触发一次性全表删除挤占交易库。

所有限流 `429` 同时返回 `retryAfterSeconds` 和标准 `Retry-After` 响应头；浏览器跨域读取时该头已显式暴露，顾客端、核销端和运营端应按该值退避，不能自动重放写操作。

顾客端在会话失效后只会自动重试安全的读取请求；下单、退款、售后等写操作会刷新会话后要求顾客再次确认提交，避免网络或会话恢复时重复创建交易与工单。新版顾客售后提交会携带 12 至 128 位的 `idempotencyKey`：同一顾客以相同标识、相同商家/券/问题描述重试时返回原工单，不会再新增工单或审计；同一标识配合不同内容返回 `409`。已发布旧客户端未携带该字段仍兼容创建。请求标识和请求摘要永不出现在顾客或运营响应中，且生产切换新版 API 前必须由受控迁移任务先创建 `IDX_support_tickets_customer_idempotency`。

登录失败和请求限流的身份哈希统一使用独立的 `THROTTLE_KEY_SECRET`；共享环境启动时会拒绝缺失、过短或复用 JWT/券码密钥的配置，避免一把密钥泄露扩大到多个安全边界。

顾客小程序券包使用 `GET /api/v1/public/vouchers/page?limit=30&cursor=...` 的游标分页：服务端始终按当前顾客范围、`createdAt DESC, id DESC` 稳定排序，游标不能扩大数据范围。旧的全量券包接口仅为已发布旧客户端保留兼容，新客户端不得再用它加载完整历史券包。上线前由受控迁移任务创建 `IDX_vouchers_customer_created (customerId, createdAt DESC, id DESC)`；预发须以接近真实历史券量执行 `EXPLAIN (ANALYZE, BUFFERS)` 并记录券包首页和翻页的 P95，确认索引生效后再放量。

运营工作台的订单、券、核销、售后和审计列表只允许浏览最新 100,000 行以内的偏移范围，防止深页查询在高并发下挤占交易数据库。需要更早的授权明细时，必须创建受控异步导出任务；它会固化权限范围、保留审计并由生命周期 Worker 分批处理。

月结账单逾期会自动暂停该商家的新售卖，已购券仍可核销或退款。平台确认全部逾期账单收款后，才可以在商家合同状态中手动恢复销售。

平台手动变更商家经营状态时，必须同时提交其当前看到的原状态和至少三字的变更说明。新版平台工作台会为该命令保留高熵 `Idempotency-Key` 直到成功；服务端在同一事务内锁定商家、先占用唯一命令记录再写入状态和审计，拒绝陈旧页面覆盖已经发生的停售、恢复或退出操作。相同命令重试返回既有状态，同键改变状态、原状态、说明或同次资料/合同修改返回 `409`，请求控制字段不会出现在任何响应或审计快照。退出必须先进入“离场收尾中”（`EXITING`）：立即停止新订单，但保留已购有效券的退款与核销；平台可查看待支付订单、待履约/退款券、待确认退款、未结售后和未结月结账单。只有全部清零后才能正式进入 `CLOSED`，且不能通过普通状态更新恢复。

门店的“暂停新售”与“停止历史券履约”分离：商家或代理可暂停新订单，已购券仍可在门店核销；只有平台管理员能在版本号和变更说明校验下停止或恢复履约。停止履约会自动停止新售、拒绝核销，并把有效未使用券放入平台的转店或补偿退款待办，避免门店永久闭店时遗漏消费者权益。

商家管理员可以在账单申诉期内提交一次申诉；申诉处理中不会自动转逾期或暂停新售。平台必须填写处理结论后账单才恢复待付款；若平台处理时原截止日已经过去，系统会从处理结论起至少保留 5 天付款宽限。申诉流程不直接修改账单金额，金额调整仍应按正式复核流程另行处理。

商家管理员可在售后工单页为本商家的一张未退款券提交异常退款申请；该申请只作为平台人工复核和补偿流程的留痕，商家和代理商不能自行结案，也不会触发真实退款。

顾客售后工单具有首次响应 SLA：新工单在下一个中国工作日 18:00 前须首次回复。运营日历通过 `CHINA_OPERATIONAL_HOLIDAYS`（法定休假）和 `CHINA_OPERATIONAL_WORKDAYS`（调休工作日）维护，支持中国调休周末；共享环境还必须设置 `CHINA_OPERATIONAL_CALENDAR_VALID_THROUGH`，并至少覆盖未来 90 天，否则 API 拒绝启动。商家、代理或平台可先回复并保持工单处理中，也可回复并结案；顾客小程序只显示面向顾客的完整回复记录，不显示内部异常退款处理。平台工作台会把逾期未首响工单列为运营待办。

## 受控数据导出

订单与核销明细不再在浏览器请求中同步拼接下载。平台、代理和商家在各自的授权商家范围内创建导出任务；核销员不能创建、查看或下载导出。新版后台会为同一次导出意图发送高熵 `Idempotency-Key`，网络重试或重复点击只返回同一任务；同一标识改动导出类型、范围或商家会被拒绝。旧客户端未提供该头时保持兼容，但只受既有频率限制保护。任务会固化当时的商家范围和中国业务日期，后台在受控批次生成 CSV，保留公式注入防护，并用现有数据密钥信封加密为最多 8 MB 的短期数据库产物。共享或生产环境中，创建任务和下载文件均要求当前设备在 10 分钟内重新验证过当前密码；发生安全事件时，撤回导出不要求重新验密，以便立即切断文件访问。

导出任务只对原请求账号可见。共享或生产环境的 API 只创建任务，独立生命周期工作器按受监控的批次领取并生成文件，避免大导出占用下单、核销和后台请求进程；本地演示保留即时处理以方便试用。每轮默认最多处理 3 份导出，可通过 `EXPORT_WORKER_BATCH_SIZE` 在 1 至 10 之间调整；`/api/public/health/worker` 会返回当前排队、处理、失败数量及最早等待时间，超过 `EXPORT_QUEUE_MAX_AGE_SECONDS`（默认 600 秒）时返回 503，供监控扩容或排障。每次查看或下载都会重新核对当前商家权限，代理归属或账号权限变化后，历史文件不可继续取得。文件在 24 小时后由生命周期工作器清除，单个任务最多下载 3 次；用户可在“导出记录”刷新、下载或撤回未过期任务，撤回会立即删除密文。请求、完成、下载、撤回、失败和过期均写入审计链，不记录 CSV 正文。

这是有容量上限的过渡实现，保证应用多实例下不依赖本机磁盘。正式运营达到更大导出量时，应在不改变任务、授权和审计契约的前提下，将密文产物替换为具备版本保留、访问日志和生命周期策略的 COS 存储适配器。

API 收到 `SIGTERM` 或 `SIGINT` 时会先将 `/api/public/health/ready` 切为 503，随后由 Nest 优雅关闭；`/live` 仍用于判断进程是否存活。部署滚动更新应给予实例足够的排空时间。

售后联系电话使用 AES-256-GCM 字段加密，平台按权限解密，代理商和商家不可读取。生产部署必须配置随机的 32 字节 Base64 活动密钥 `DATA_ENCRYPTION_KEY` 和稳定标识 `DATA_ENCRYPTION_KEY_ID`，并纳入密钥管理；历史明文工单应在正式上线前备份、转换和复核。

密钥轮换采用先双读、后重加密、再移除旧密钥的顺序。新密文为 `v2.<keyId>...`；旧 `v1` 密文会依次尝试活动和退役密钥。先部署新的活动密钥和标识，并把旧密钥写入 `DATA_ENCRYPTION_PREVIOUS_KEYS`（`旧标识:旧Base64密钥`，多个以逗号分隔）。确认应用可以读取历史工单后，以受控批次运行：

```powershell
$env:SENSITIVE_DATA_REENCRYPT_MAX_ROWS = '1000'
npm run sensitive-data:reencrypt -w @local-deals/api

# 预检结果与备份核验无误后才允许写入。
$env:SENSITIVE_DATA_REENCRYPT_APPLY = 'true'
npm run sensitive-data:reencrypt -w @local-deals/api
```

该工具拒绝内嵌演示库、缺少活动密钥或密钥标识的运行环境，不输出任何联系电话；写入使用旧密文条件更新，避免覆盖并发产生的新工单。所有历史记录完成重加密并完成恢复演练后，才可从配置中移除退役密钥。

新写入的审计事件先与业务数据在同一事务写入 `audit_outbox`，其中事件载荷使用独立 `AUDIT_LOG_SIGNING_KEY` 生成 HMAC 摘要；业务请求不再争抢全局审计链状态行。套餐、售后、账单、人员管理和密码重置等服务端写操作均将业务写入和 outbox 交由同一个事务管理器提交。生命周期 Worker 以 `AUDIT_OUTBOX_BATCH_SIZE`（默认 100）领取事件、复核摘要后才写入 HMAC 顺序链，记录前序摘要、序号和签名。平台管理员可在“平台安全审计”查看链完整性、待签名和隔离事件；完整性扫描按 `AUDIT_CHAIN_VERIFY_BATCH_SIZE`（默认 500）游标分批读取 `(chainVersion, chainSequence)`，不会将全量历史装载到 API 内存，但仍是 O(n) 工作，应在低峰运行并记录时长。签名、顺序或 outbox 摘要不匹配都会显示异常，隔离事件不会自动删除或重试。共享环境必须使用独立随机的 32 字节 Base64 签名密钥，不能与 JWT、券码或数据加密密钥复用。迁移前既有审计记录保留为历史留痕，签名链从完成迁移后产生的新记录开始；生产阶段还应将每日链末摘要锚定到受保留策略保护的对象存储。

当前代码只能作为本地/测试演示运行。顾客端会申请一个仅演示环境可用的短期签名会话，公开交易接口不再接受 `X-Customer-Id`。生产环境会主动拒绝启动，直到接入经审查的微信消费者身份、支付回调和退款适配器；不得把 `MockPaymentProvider` 或演示顾客会话带入生产。共享环境即使为了联调后台而启动，也会选择不可用支付提供方并拒绝新支付订单，不会把 Mock 通道误当真实收款。

`/api/v1/public/orders/:orderId/mock-confirm` 仅在 `development` 或 `test` 环境可用；共享、预发和生产环境即使持有顾客令牌也会得到不存在响应。真实支付必须改由支付适配器的验签回调和查单补偿推进订单状态，不能复用该接口。订单、库存占用和支付意图会在同一数据库事务写入 `payment_outbox`；通道调用在事务外可靠重试。验签后的 `payment_events` 按通道事件 ID 去重，金额、商家、订单状态全部通过后才会原子生成券。完整接入契约见 [PAYMENT_INTEGRATION.md](PAYMENT_INTEGRATION.md)。

运营后台会话与顾客会话使用不同 JWT 受众校验，不能跨端复用。运营后台令牌与用户资料仅保留在浏览器会话存储中，关闭浏览器后需要重新登录；旧版本遗留的本地持久令牌会在下次打开时一次性迁移并删除，避免共享电脑长期保留运营权限。共享或生产环境中，费率提交与复核、异常退款审批与执行、退款重试、停业补偿、月结生成、账单收款确认/入账/开票、核销员工启停、受控数据导出创建/下载以及下级密码重置，均要求当前设备会话在 10 分钟内重新验证过当前密码。月结生成和员工启停会携带高熵 `Idempotency-Key`：相同请求重试不会重复生成账单、撤销会话或写审计，同键改账期、员工或启停方向返回 `409`；旧工作台省略请求头仍兼容，部署新版工作台前必须先完成 `monthly_bill_generation_commands` 与 `staff_active_commands` 的受控迁移。验证时间仅保存在对应会话，不保存密码；改密、退出或会话失效会立即使其失效，并写入签名审计链。本地演示默认不强制该步骤；需要演练时设置 `ENFORCE_SENSITIVE_ACTION_STEP_UP=true`。退款支付失败后，券保持不可核销；顾客券包仅在退款明确失败时提供“重新确认退款”，平台管理员也只能重试明确失败的退款，且始终复用原支付幂等键。

核销助手会按核销员账号显示授权门店。员工轮班时先选择当前工作门店，该选择只保存于该账号的本机小程序；扫描预览与提交核销均携带当前工作门店，服务端要求其与员工授权和券绑定门店一致。门店不一致的券只能提示切换，不会生成核销记录。

## 开户与授权进度

管理后台提供不依赖公司资质的开户与授权状态机：草稿、待补齐资料、已提交、待主体确认、审核中、已开通、授权中、小程序可发布、审核失败。代理商仅能推进资料准备与提交，商家仅能确认主体与发起授权，平台负责审核结果和小程序可发布确认；每次状态变化都会写入审计记录。此模块仅保存流程状态和运营说明，不接收证照原件，也不会调用微信注册、授权或发布接口。

本机稳定 API 默认地址是 `http://localhost:3001/api/v1`。管理后台开发服务器默认将同源 `/api` 请求代理至 `http://localhost:3001`；需要连接其他 API 时，设置 `VITE_API_PROXY_TARGET`，或在构建时将 `VITE_API_URL` 精确设置到 `/api/v1`。将 `apps/miniprogram-customer` 和 `apps/miniprogram-verifier` 分别导入微信开发者工具；顾客端可切换 5 家演示商家。首次导入顾客端后在微信开发者工具中构建 npm，生成二维码组件依赖。版本兼容、弃用期限和 v2 触发条件见 [API_VERSIONING.md](API_VERSIONING.md)。

共享环境把平台、代理、商户和核销工作台分别部署到独立子域名，并以 `VITE_WORKSPACE_ROLE` 固定各自允许登录的角色；浏览器来源由 `CORS_ORIGINS` 精确白名单控制。完整的域名、入口层和发布检查见 [SUBDOMAIN_DEPLOYMENT.md](SUBDOMAIN_DEPLOYMENT.md)。
